# Замороженные SDK и runtime

При возобновлении серверной сборки брать точные `CMAKE_COMMAND`,
`CMAKE_MAKE_PROGRAM`, compiler и toolchain из проверенного рабочего
CMake cache. Не полагаться на PATH интерактивного SSH-сеанса при запуске
через systemd. Новый runtime размещать отдельно от прежнего; отказ
до компиляции сохранять как отдельную попытку.

При новой конфигурации переносить также явные feature flags проверенного
cache и фиксировать их в задании. Совпадение compiler/Qt само по себе
не означает совпадения профиля сборки. Пути output/runtime всегда задавать
новые; старые cache и исходники не обновлять для исправления нового запуска.

Для нового worktree сабмодуля проверять `git rev-parse --show-toplevel`
до checkout и после настройки sparse checkout. Относительный `core.worktree`
общего submodule Git-конфига может разрешиться в каталог метаданных.
Не обходить production-проверку alias и не исправлять общий конфиг
действующих деревьев. При включённом `extensions.worktreeConfig` задавать
нужный корень только в конфиге собственного нового worktree и повторять
проверку всех исходных HEAD, корней и tracked status.

Перед отправкой построения графиков проверять импорт Matplotlib и Agg
в точной Python-среде фонового задания либо явно задавать подготовленный
путь библиотек renderer. Наличие Matplotlib на другом исполнителе не
подтверждает готовность выбранного. Отказ рисунков не требует нового
расчёта модели; первичные данные и успешные предыдущие проверки сохранять.

Любые Python-опросы и проверки, импортирующие модули замороженного SDK,
выполнять с `python -B` и запрещать запись байткода до первого такого
импорта. Это относится и к чтению состояния процессов. Не исключать
`__pycache__` из строгой проверки файлового состава. Подтверждённый
служебный кэш удалять только после проверки закрытия задач и сохранности
всех объявленных исходных файлов; исходную неудачную проверку сохранять.

# Объявления запусков в Git

При подготовке нового SDK из sparse worktree явно включать новые исходники
и заголовки изменённых компонентов в физическое дерево до фиксации
namespace. Для обязательных новых файлов проверять наличие и Git blob;
чистый `git status` не доказывает, что sparse checkout материализовал их.
Namespace действующих и уже замороженных попыток не менять: исправленный
состав оформлять отдельной попыткой с сохранением прежнего отказа сборки.

Новые отдельные Git-репозитории управляющих файлов запусков создавать
с `.gitattributes`, содержащим `* -text`, до первого `git add`. Это сохраняет
точные байты JSON, командных файлов и контрольных сумм независимо от
системного `core.autocrlf`. Не менять управляющие файлы действующего опыта.
Если у исторического запуска обнаружена нормализация LF/CRLF, сохранить
обе формы и явно перечислить различия; побайтовое совпадение не объявлять.

Перед использованием результата production-runner в новом координаторе
прочитать фактический контракт возвращаемого документа. Не угадывать
имена полей и не подменять их предполагаемыми путями: для первичных
файлов сохранять явные `file_record` и штатный run manifest. Ошибка
оформления метаданных после успешного расчёта не является основанием
повторять сам расчёт; исправлять постобработку, сохраняя исходный отказ.

Для physical DATA разных версий получать эффективный порог через
`audit_physical_model_data(..., frozen=True)['effective_threshold']`.
DATA2 не имеет верхнеуровневого поля `threshold`; DATA3 имеет его.
Не переносить расположение поля из одной версии в другую и не заменять
отсутствующее значение предположением о default.

При переносе анализа на другую серию не наследовать её число членов
архива как универсальную константу. Проверять зафиксированную полную
инвентаризацию нового комплекта и содержательные ожидания по наблюдениям,
файлам и связям. Различия состава, включая реально загруженные библиотеки,
объяснять и проверять; прежнюю неудачную проверку не удалять.

Перед отправкой Python-координатора проверять синтаксис его файла и
каждого создаваемого им Python-файла. Успешный compile внешнего текста
не доказывает корректность вложенного текста. Предпочитать отдельные
файлы с точными байтами; не создавать строковые литералы с переводами
строк через несколько слоёв экранирования.

Адреса файлов удалённого Linux из Windows формировать строками POSIX
или PurePosixPath; локальный Windows Path преобразует разделители.
Проверять абсолютность пути на целевой ОС до записи. Длительную подготовку
исходников выполнять в собственной отслеживаемой unit с журналом и
идентичностью процесса. При sparse checkout заранее передавать через Git
все требуемые blobs выбранного scope; не оставлять скрытую загрузку
отсутствующих Docs во время подготовки Python-only дерева.

В ответ инструмента выводить компактные сводки. Полные списки leases,
первичных файлов и git status незавершённого checkout сохранять отдельно;
выводить число записей, нужные состояния и ограниченные выдержки.

Для unittest проверять фактические testsRun и skipped вместе с errors/failures.
Returncode0 при нуле tests и пропущенных setUpClass не является положительной
проверкой. До запуска corpus-dependent набора проверить все обязательные
fixture-переменные и источники; отсутствие корпуса не заменять фиктивными данными.

После удаления transient systemd unit с `--collect` ответ `show` может
содержать значения по умолчанию `Result=success/ExecMainStatus=0` даже
после отказа. Не считать их положительной приёмкой: проверять наличие
самой unit, kernel handle, сохранённые первичные результаты и журнал.
Закрытие процесса и успешность выполненной операции — отдельные факты.

Проверки provenance должны учитывать роль процесса. Отсутствие карты
загрузки вспомогательного CLI-процесса явно сохранять как unknown;
не выдавать его за захваченную карту. Для основного научного процесса
обязательные проверки не ослаблять. При архивации сохранять разные
статусы раздельно и не объявлять весь комплект полностью подтверждённым
по provenance, если часть вспомогательных сведений неизвестна.

При подготовке удалённых управляющих программ не выполнять глобальные
строковые замены после включения текста вложенного worker: такая замена
может изменить пути исходного опыта внутри программы. Пути источников,
аудита, собственных выходов и имена попыток задавать раздельными полями.
Перед фиксацией и после передачи проверить точные байты worker и то,
что источник аудита существует и отличается от каталога новых выходов.
Отказ публикации сохранять отдельно; готовый Train из-за него не повторять.

При передаче в partial clone одного наличия prerequisite commit недостаточно:
тонкий Git pack может ссылаться на отсутствующие базовые blobs. Для нового
дерева инструментов заранее передавать также pack с локально разрешёнными
delta bases и blobs выбранного физического scope; проверять импорт до checkout.
Не оставлять скрытую подгрузку объектов во время фоновой подготовки.
Для отдельного Python-only дерева использовать `git fetch --no-recurse-submodules`:
его SDK/runtime проверяются отдельно, подключать или обновлять сабмодули этого
дерева ради импорта Python не требуется. Эта настройка команды не разрешает
ослаблять проверку полной closure нативного SDK.

При переносе Windows SDK локальный clone связанного worktree может отказать
по владельцу каталога Git, даже когда чтение самого worktree разрешено.
Не расширять глобальные safe.directory и не менять владельца исходной копии.
Использовать новый private SDK с точными Git packs одного commit/его trees
и всех blobs объявленного физического scope. Границу shallow новой копии
фиксировать явно; опубликованную историю и SHA не менять. До сборки
сравнивать полную физическую namespace и hashes с проверенным SDK-источником.

На Windows проверять Git не только в SSH-сеансе, но и под реальным
пользователем Task Scheduler. Каталог, созданный SSH-сеансом с владельцем
BUILTIN/Administrators, может быть отклонён Git фонового User. Если worker
должен фиксировать подготовленные спецификации, создавать его отдельный
Git-каталог управления самим фоновым пользователем, сохраняя точные байты
исходной декларации и её Git-комплект. Не менять владельца прежнего каталога
и не расширять global safe.directory. stderr всех управляющих Git-команд
записывать явно: переназначение Python sys.stderr само по себе не направляет
OS stderr дочернего процесса в этот файл при запуске через pythonw.

# Проверка формата первичного архива

Перед выбором аудитора прочитать `kind`, версию схемы и фактический
состав пакета. `verify_pipeline_archive` проверяет семейство pipeline
с подписанными `run-manifest.json`. Компактный `compact_native_primary`
восстанавливать через штатный `restore_native_bundle`, затем выполнять
соответствующий аудит native gate либо подготовленного диагностического
опыта. Целостность файлов и научная валидность — отдельные проверки.
Для сохранённых регулярных glog-алиасов без legacy run manifest явно
объявлять `retain-regular-glog-aliases-v1`: сохраняются все имена и байты,
происхождение исходной файловой ссылки этим не подтверждается. Исходный
отказ сохранять; данные и манифесты не достраивать ради прохождения
аудитора другого формата. Временное восстановление большого пакета
размещать в собственной объявленной cache-папке общего диска и удалять
только после проверки и сохранения результата; исходные объекты архива
оставлять неизменными.
