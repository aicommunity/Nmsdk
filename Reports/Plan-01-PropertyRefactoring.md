# План рефакторинга ядра Rdk - унификация свойств и оптимизация

## Цели рефакторинга

1. **Унификация типов свойств:**

   - Объединение Parameters, States, Inputs, Outputs в единый UProperty
   - Удаление реликта ipComp (указатели на компоненты)
   - Упрощение API

2. **Улучшение производительности:**

   - Устранение узких мест в системе UProperty
   - Оптимизация доступа к данным
   - Снижение накладных расходов на синхронизацию

3. **Снижение сложности:**

   - Упрощение иерархии классов свойств
   - Улучшение читаемости кода
   - Упрощение механизмов подключения свойств

4. **Создание тестовой инфраструктуры:**

   - Unit тесты для критических компонентов
   - Integration тесты для проверки взаимодействия
   - Непрерывный мониторинг функциональности

## Анализ текущей архитектуры свойств

### Типы свойств

**Текущая структура:**

- **Parameters (ptParameter)**: параметры компонента, используют `ULProperty<T, OwnerT, ptPubParameter>`
- **States (ptState)**: состояния компонента, используют `ULProperty<T, OwnerT, ptPubState>`
- **Outputs (ptOutput)**: выходные данные, используют `UPropertyOutputData<T, OwnerT, ptPubOutput>`
- **Inputs (ptInput)**: входные данные, используют `UPropertyInputData<T, OwnerT, ptPubInput>`

**Наблюдения:**

1. Parameters и States структурно идентичны - оба используют базовый `UProperty<T, OwnerT, type>`
2. Outputs могут быть идентичны Parameters/States - различие только в флаге типа
3. Inputs более сложные из-за поддержки подключений, но базовая структура та же
4. Все четыре типа можно объединить в единый `UProperty<T, OwnerT, type>` с различиями только в флагах

### Реликт ipComp (указатели на компоненты)

**Текущее состояние:**

- `ipComp = 2` - флаг для указателей на компоненты (устаревший)
- `ipData = 1` - флаг для простых данных (актуальный)
- Enum значения: `ipCompSingle`, `ipCompRange`, `ipCompList` определены, но не используются активно

**Использование GetItem():**

- GetItem() используется в библиотеках для получения компонентов через подключенные output свойства
- Найдено в:
  - NPulseNeuron.cpp: `Inputs.GetItem(i)` для получения синапсов
  - NPulseSynChannel.cpp: `ChannelInputs.GetItem(n)->GetOwner()` для получения компонентов
  - NPCNElement.cpp: `MotionControl.GetItem()` для получения NEngineMotionControl
  - NMultiPositionControl.cpp: `PositionControl.GetItem(i)` для получения NPositionControlElement
- **Важно**: GetItem() работает через `ConnectedOutputs[index]->GetOwner()`, что является нормальной функциональностью, а не реликтом ipComp
- Реликт ipComp не используется активно - можно безопасно удалить

### Выявленные узкие места производительности

1. **Мьютексы на каждое свойство:**

   - Каждое свойство создает UGenericMutex при инициализации
   - Большинство свойств не нуждаются в синхронизации
   - Решение: опциональные мьютексы только для shared свойств

2. **Копирование данных при GetData:**

   - Строка 585: `v = dynamic_cast<UVBaseDataProperty<T>*>(this->ConnectedOutputs[0])->GetData()`
   - Копирование больших матриц/векторов на каждом доступе
   - Решение: кэширование с проверкой времени обновления

3. **Множественные виртуальные вызовы:**

   - Цепочка: GetData -> ExternalDataSource? -> IsConnectedFlag? -> GetData
   - Решение: инлайнинг для частых путей доступа

4. **dynamic_cast в горячих путях:**

   - Используется в GetData для подключенных свойств
   - Решение: хранение типизированного указателя вместо базового

5. **Проверки на каждом доступе:**

   - ApplyOutputUpdateTime вызывается в каждом operator()
   - Решение: ленивое обновление только при необходимости

## План рефакторинга

### Этап 0: Исследование и аудит

**Задачи:**

1. Полный аудит использования ipComp в кодовой базе
2. Документирование всех использований GetItem() в Libraries
3. Подтверждение, что ipComp не используется активно
4. Анализ паттернов использования свойств в Libraries

**Файлы для исследования:**

- Все файлы в Libraries с использованием GetItem()
- Поиск всех упоминаний ipComp
- Анализ UBasePropCreatorTempl.h для понимания создания свойств

**Результат:**

- Отчет об использовании ipComp (ожидается: не используется)
- Документация паттернов использования GetItem()
- План миграции для Libraries

### Этап 1: Унификация типов свойств

**Файлы:**

- `Rdk/Core/Engine/UProperty.h`
- `Rdk/Core/Engine/UComponent.h`
- `Rdk/Core/Engine/UBasePropCreatorTempl.h`

**Изменения:**

1. Объединить все четыре типа (Parameters, States, Inputs, Outputs) в единый `UProperty<T, OwnerT, type>`
2. Убрать алиасы ULProperty, UCLProperty, UPropertyInputData, UPropertyOutputData (оставить для обратной совместимости как deprecated)
3. Упростить логику различий - использовать только флаги типа (ptParameter/ptState/ptInput/ptOutput)
4. Упростить UIPropertyInput/UIPropertyOutput - сделать их простыми интерфейсами без дублирования
5. Убрать реликт ipComp (ipCompSingle, ipCompRange, ipCompList) из enum и кода
6. Упростить GetItem() - оставить только для работы с подключенными output свойствами

**Метрики успеха:**

- Единый класс UProperty для всех типов
- Удаление ipComp из кодовой базы
- Сохранение обратной совместимости через deprecated алиасы
- Все тесты проходят

### Этап 2: Оптимизация доступа к данным

**Файлы:**

- `Rdk/Core/Engine/UProperty.h`
- `Rdk/Core/Engine/UPropertyEndpoints.h`

**Изменения:**

1. Добавить опциональные мьютексы (только для shared свойств)
2. Реализовать кэширование для подключенных свойств с проверкой UpdateTime
3. Заменить dynamic_cast на типизированные указатели в ConnectedOutputs
4. Инлайнить частые пути доступа (GetData для неподключенных свойств)
5. Оптимизировать operator() для избежания лишних проверок

**Метрики успеха:**

- Снижение времени доступа к свойствам на 30-50%
- Устранение ненужных копирований данных

### Этап 3: Упрощение иерархии классов

**Файлы:**

- `Rdk/Core/Engine/UProperty.h`

**Изменения:**

1. Объединить UVBaseProperty и UVProperty где возможно
2. Упростить UPropertyLocal, убрав дублирование логики
3. Вынести общую логику подключений в отдельный миксин
4. Упростить специализации для контейнеров

**Метрики успеха:**

- Уменьшение глубины иерархии с 5 до 3-4 уровней
- Улучшение читаемости кода
- Единая точка входа для всех типов свойств

### Этап 4: Оптимизация поиска свойств

**Файлы:**

- `Rdk/Core/Engine/UComponent.h`
- `Rdk/Core/Engine/UComponent.cpp`

**Изменения:**

1. Добавить индексацию свойств по имени для O(1) доступа
2. Кэшировать результаты FindProperty
3. Оптимизировать AddLookupProperty

**Метрики успеха:**

- O(1) доступ к свойствам вместо O(n)
- Ускорение инициализации компонентов

## Риски и митигация

1. **Риск:** Рефакторинг может сломать существующий код

   - **Митигация:** Постепенные изменения, полное тестовое покрытие перед рефакторингом

2. **Риск:** Изменения могут повлиять на библиотеки

   - **Митигация:** Тщательное тестирование всех Libraries, обратная совместимость API через deprecated алиасы

3. **Риск:** Сложность рефакторинга может быть недооценена

   - **Митигация:** Поэтапный подход, возможность отката изменений

4. **Риск:** GetItem() может использоваться неожиданным образом

   - **Митигация:** Полный аудит использования перед изменениями, сохранение функциональности GetItem() для подключенных свойств

5. **Риск:** Удаление ipComp может сломать старый код

   - **Митигация:** Тщательный поиск всех использований ipComp, постепенное удаление с предупреждениями компилятора

6. **Риск:** Унификация может усложнить код для некоторых случаев

   - **Митигация:** Сохранение специализаций где необходимо, тщательное тестирование всех сценариев
