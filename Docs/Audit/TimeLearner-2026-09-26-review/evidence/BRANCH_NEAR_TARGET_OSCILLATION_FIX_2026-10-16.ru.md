# Branch: учёт near-target осцилляции Rs — 2026-10-16

## Наблюдение

В трассе Branch W04, 100 мс, `N1`, PSI off на итерациях 50–80 активный TipR находился примерно между `717.43 kΩ` и `718.16 kΩ`, а `amp_dt = InitialSomaPotential - MaxIterSomaAmp` чередовался около `+1.1e-5` и `−3.4e-5`. Остаток каждый раз оставался больше `kAmpNormEps=1e-5`, но намного меньше существующей `kAmpOscillationBand=0.005`.

Параметрический EOL Branch уже разрешает завершить обучение после трёх no-improve событий, если длина синхронизирована и ошибка находится внутри этой полосы. Однако счётчик циклически становился `0/1`: при переходе `−3.4e-5 → +1.1e-5` абсолютная ошибка уменьшалась более чем вдвое. Код считал это существенным улучшением, хотя знак поменялся и следующая итерация снова перескакивала через цель.

## Исправление

В `NNeuronTimeLearnerBranch::ChangeSynapseResistanceStatus` уменьшение `|dt|` сбрасывает near-target no-improve счётчик только если остаток остался по ту же сторону цели. Переход через ноль внутри near-target полосы учитывается как осцилляция. При выходе за эту полосу сохранено прежнее правило meaningful-drop. Достижение `AmpNormEps`, значение `kAmpOscillationBand`, число необходимых событий и EOL-критерий не менялись.

Classic не менялся: хотя соответствующий счётчик есть и в Classic, в имеющихся данных этот механизм доказан для конкретной Branch-трассы. Перенос на Classic требует собственной трассы или контрпримера.

## Проверка аналогичных Classic-данных

В доступных Classic Phase6 материалах не найдено независимой трассы с тем же near-target циклом. Точный Linux Release повтор `phase6_480` на текущем Classic-коде завершился явным `Need=1` из-за `Rs=Rmax=10 GΩ` и `amp_dt=−0.275999` на активном входе — далеко за `kAmpOscillationBand`; см. [отчёт точного PHASE6 повтора](PHASE6_EXACT_REPLAY_STATUS_2026-10-16.ru.md). В исторических реконструкциях PHASE6 на итерациях с плато остатки первых трёх входов были около `−0.064`, `−0.064`, `−0.051` при Rs=100 GΩ; в паре после первого sync зафиксированы `−0.132`, `−0.0237`, `+0.0158`, причём пик третьего входа невалиден. Эти состояния показывают другие проблемы поиска/границ, а не знакочередующуюся ошибку около epsilon. См. [аудит итераций PHASE6 до октября](../../../../Bin/Configs/SpikeSamples/StructTrain/TimeLearnerMatrix/diagnostics/phase6_historical_positive_replay_pre_oct_iteration_audit_2026-10-12.csv), [аудит после изменений 6 октября](../../../../Bin/Configs/SpikeSamples/StructTrain/TimeLearnerMatrix/diagnostics/phase6_historical_positive_replay_oct06_iteration_audit_2026-10-12.csv) и [пару фиксации Rs после sync](../../../../Bin/Configs/SpikeSamples/StructTrain/TimeLearnerMatrix/diagnostics/phase6_first_sync_rs_freeze_iteration_audit_2026-10-12.csv).

Вывод ограничен доступными записями: он не доказывает, что аналогичный сброс счётчика никогда не блокирует Classic. В Classic исходнике есть похожее условие, поэтому будущий точечный Classic повтор следует писать с `amp_dt`, `NoImproveResistanceCount`, `ResistanceStatus` на каждой итерации. Менять Classic до появления такой трассы оснований нет.

## Регрессионная проверка

Новый C++ тест подаёт на Branch контролируемую последовательность ошибок `+1.1e-5 → −3.4e-5 → +1.1e-5`. Он проверяет накопление трёх no-improve событий, снятие блокирующего `ResistanceStatus` и прохождение существующего `AllSynapsesNormalized()` near-target EOL. До исправления третий отсчёт сбрасывал счётчик; после исправления тест проходит.

Проверка выполнена сборкой `Test_PulseLib_StorageComponents` в конфигурации Windows Release и запуском CTest: `1/1 passed`. Отдельный фильтр нового случая также прошёл (`1/1`). Для интеграционного запуска понадобился Release DLL PATH. В `Tests/Integration/Libraries/CMakeLists.txt` цель исправлена на импортированную `GTest::gtest`: в этой конфигурации `find_package(GTest)` находил пакет, но прежняя ссылка `gtest` превращалась в неразрешённое голое имя `gtest.lib`.

## Границы вывода и следующий шаг

Это исправление устраняет подтверждённую блокировку EOL в воспроизведённой последовательности, используя уже существующую политику допуска. Оно не доказывает естественную сходимость полного обучения и не оценивает классификацию. Повтор W04 на исправленной Linux Release Console и измерение detection, Acc и FP не выполнены: с этой рабочей станции TCP/22 к `.11`, `.12` и `.17` после переподключения пока не устанавливается.

После восстановления маршрута нужен один свежий Branch W04 `100 ms / N1 / PSI off` повтор с тем же Train/Test manifest и логированием `amp_dt`, `TipR`, `NoImproveResistanceCount`, `ResistanceStatus`, `Need` и причины завершения. Классификацию оценивать только после штатного C++ завершения. Classic проверить отдельно только при наличии его собственной трассы с пересечениями около `AmpNormEps` и тем же сбросом счётчика.
