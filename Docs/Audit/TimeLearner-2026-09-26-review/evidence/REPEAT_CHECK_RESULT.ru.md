# Повторная проверка отказов TimeLearner

Дата: 2026-10-08. Проверка выполнена на отдельном чистом checkout; исходные рабочие деревья и старые run bundles не изменялись.

## Что именно различаем

В отчётах теперь три независимых результата:

1. **Сходимость тренера** — достиг ли C++-тренер своего конечного состояния (`Need=0` / `TrainingPhase=Done`). Таймаут при `Need=1` — это «не сошлось за данный бюджет», а не доказательство невозможности решения.
2. **Качество PostTune-разделения** — `PostTuneResult` и метрики C++ PostTune. `result=2` — `NonSeparable` на этом наборе проб.
3. **Детекция/разделение на Test** — результат отдельного inference/gate: ожидаемый шаблон детекции, ложные срабатывания или отсутствие измеримого результата.

Это различие важно: C++ `FinalizePostTuneMid` штатно переводит тренер в `Done` и снимает `Need` также при `PostTuneResult=NonSeparable`. И наоборот, `PostTuneResult=2` сам по себе не означает, что итоговый Test обязательно не распознает цель: оба положительных контроля прошли Test gate при таком результате PostTune. Итерационный audit пишет состояние до вызова финализатора, поэтому последняя строка audit может содержать `Need=1`, а сохранённое состояние после финализации — `Need=0`.

Генератор будущих отчётов дополнен отдельными полями `training_convergence`, `posttune_quality` и `detection_quality`; это постобработка C++-результатов, без управляющей логики обучения.

## Дефекты реализации и ограничения

### Дефекты экспериментального harness, подтверждённые и исправленные

- Два phase gate-скрипта обращались к жёстко заданному checkout/Console. Первый неправильный маршрут был исключён из результатов; скрипты исправлены так, чтобы брать Console из активного checkout или `NMSDK_CONSOLE`.
- Cold reset contract определял тип тренера по `NeuronClassName`, хотя у Branch тренер объявлен отдельным компонентом `<NeuronTimeLearnerBranch>`. Из-за этого отчет ошибочно мог сообщить `is_branch=false`. Обнаружение исправлено; runtime audit подтверждает Branch, `active_dendrite=3`, длины после `BuildStructure()` `[1,1,1,1]` (временный reference length 0 в Reset затем ограничивается до 1).

JSON `cold_reset_contract` в bundles текущего запуска был создан старой версией helper до этого исправления; если он называет такой Branch-run классическим, это поле ошибочно. Для этих запусков источником факта о типе тренера считать `trainer=branch` из C++ audit и runtime-вектор/active anchor, а не устаревший JSON.

Это ошибки измерения/маршрутизации, а не доказанные дефекты алгоритма обучения. В текущих выбранных отказах не найдено подтверждения потери C++-изменения или неверного срабатывания EOL. Известное исправление классического epsilon (`int` → `double`) и исправление SoftCold-инициализации предшествуют этой проверке; см. [историю исследования](SOFTCOLD_RESEARCH_HISTORY.ru.md).

### Что пока нельзя утверждать

- Нельзя объявлять 4 неудачных стандартных gate случая доказательством математической неразделимости: отсутствующая C++-детекция и отрицательный PostTune gap подтверждают отказ на этих пробах/конфигурациях, но не невозможность альтернативного решения.
- Нельзя объявлять три остановленных D-кейса объективно несходящимися: они были остановлены по времени с `Need=1`, EOL=0 и меняющейся длиной.
- `Keep/Search`, `SoftColdOff`, полный набор `NonSeparable` и все 36 исторических full49 FAIL этой выборкой не переоценены.
- PASS-контроли подтверждают работоспособность тракта в конкретных режимах, но не исправность каждого отдельного свойства Classic/Branch.

## Следующий план исследования

1. **Сначала закрыть классификацию каждой исторической FAIL-строки** по сохранённым bundles, разделив convergence / PostTune quality / Test detection; к повторному эксперименту отправлять только строки без достаточных runtime-данных.
2. **Для завершённых, но тихих случаев** сохранить по одному минимальному повтору на Classic и Branch: C++ reset + terminal audit, PostTune `result/gap/landscape_ok`, Test CSV и код причины отсутствия `fires`. Не менять `Need`, `LandscapeOk`, Acc/fires или SyncTol.
3. **Для br25_on** отдельно измерить пороговый диапазон target/foil на копиях результата и записать кривую компромисса. Это измерительный эксперимент, не изменение алгоритма или принятие Python-порога тренером.
4. **Для D-кейсов** сначала решить, нужен ли длительный прогон; если да, проводить отдельную ограниченную серию с сохранением audit и Rmax/length-trajectory. Не повторять полную full49 до появления вопроса, на который такой запуск может ответить.
5. Любую предполагаемую ошибку тренера подтверждать минимальной C++-проверкой Classic и Branch отдельно. Только доказанный дефект менять в соответствующем C++-классе; затем повторять затронутый кейс и положительный контроль. Скриптам оставить подготовку/запуск/архивацию/анализ.
