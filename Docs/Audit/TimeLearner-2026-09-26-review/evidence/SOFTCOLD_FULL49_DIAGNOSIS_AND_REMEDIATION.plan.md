## Цель и границы

Установить для причин 0/49 SoftCold PASS, какие из них вызваны ошибкой реализации/экспериментального учёта, какие означают незавершение или отказ при выбранной политике обучения, а какие относятся к качеству уже завершившегося результата. Для ограниченных диагностических прогонов выбрать минимальный набор, который проверит регрессию относительно прежних PASS и основные режимы Classic/Branch.

Рабочая гипотеза — это не вывод о математической разрешимости. Конечное число запусков может подтвердить поведение тренера в данных условиях, но не математическую невозможность обучения.

**Инварианты исследования:**

- Вся логика обучения и каждое изменение состояния тренера остаются в C++ (`NNeuronTimeLearner` и `NNeuronTimeLearnerBranch`). Скрипты только готовят изолированный запуск, вызывают Console, сохраняют артефакты и анализируют их.
- W3/length escape остаётся выключенным. Отказ при неустранённом overshoot на `ResistanceMax` считается штатным исходом текущей политики, пока исследование не докажет дефект вычисления границы или её применения.
- Не менять `Need`, `LandscapeOk`, пороги Acc/fires или SyncTol ради PASS. Обучение, качество разделения и обнаружение цели учитывать раздельно.
- Сборки и эксперименты выполнять только на Linux-сервере. Не запускать их на текущей рабочей станции. До доступности сервера не начинать зависимые от него шаги.
- Сохранять первичные журналы и provenance до очистки временных файлов. Из-за риска заполнения диска не копировать без необходимости целые деревья данных; сначала сохранять компактный аудит и выбранные run bundles.

## Шаг 3. Снять причинную трассу и классифицировать каждый результат

Для каждого выбранного случая зафиксировать состояние после C++ reset и последовательность аудита до терминального исхода или лимита. Использовать уже имеющиеся read-only iteration audit поля. Если нужного поля в логе нет, добавить только диагностическую запись в C++; она не должна менять вычисления и состояние тренера.

Минимальные поля записи:

- iteration, phase, `Need`, `TrainingFailureReason`, reset kind, `dt`;
- target `Rm` и фактический `Rs` каждого tip; `Rs/Rm` каждого tip; полученные `ResistanceMin/Max` и configured ratio;
- длины до/после итерации и причина каждого изменения; для Branch — active pulse, индекс текущего участка/ветви, reverse-order и anchor;
- raw peak values, `peak_valid`, окно/импульс измерения, `eol_sync`, `eol_amp`, TipR delta/direction;
- счётчики AmpNorm/EOL; exit code либо сигнал, достигнутый `-t`, решение monitor и сохранённые gate-метрики.

Для каждого кейса назначить **одну основную категорию** и при необходимости вторичную:

| Категория | Критерий присвоения |
|---|---|
| `implementation_defect` | Трасса показывает нарушение контракта: потеря запрошенного обновления, неверный reset/anchor, некорректная граница/Clamp, решение EOL вопреки валидным измерениям или подтверждённая ошибка диагностики C++ |
| `configured_limit_Rmax` | C++ завершил с `failure_reason=1`; tip действительно на вычисленном Rmax, синхронизация/overshoot совпадают с условием кода. Это честный отказ на данном лимите, не математическая невозможность |
| `not_converged` | По окончании разрешённого времени `Need=1`, терминального C++ failure нет; далее указать подтип: invalid peaks, desync/oscillation, no progress, progress but time limit, либо неизвестно |
| `quality_or_detection` | Только после `Need=0`: separability недостаточна, целевая детекция отсутствует или fires/Acc не соответствуют ожиданию; значения указывать независимо |
| `insufficient_data` | Нет достоверного run ID/audit/config или сигналы противоречат друг другу |

Не классифицировать отсутствие gate-детекции при `Need=1` как посттренировочное качество. `Need=1` само по себе не доказывает ни Rmax-упор, ни невозможность решения; `Need=0` само по себе не подтверждает качество.

## Шаг 4. Проверить Rs/Rm, Rmax и нижний край диапазона

1. Для каждого параметрического случая сверить формулы исходников с фактической топологией и `Rm` всех tips. Для общей скалярной пары записать фактическое допустимое отношение каждого tip:
   `ratio_min_i = ResistanceMin / Rm_i`, `ratio_max_i = ResistanceMax / Rm_i`.
   Также проверить условие существования общей пары `max(Rm)/min(Rm) <= q²`. Фактический верхний предел для tip — `min(Rm)*q/Rm_i`; он может быть ниже `q`.
2. Для `phase6_480` и при необходимости `pa00_baseline` установить: достиг ли каждый tip своей фактической границы, какие пики и overshoot остались, прошёл ли sync, менялся ли `dt`, и было ли `failure_reason=1` записано ровно один раз после корректного C++ reset.
3. Для `asym100_gen` проверить конечность/валидность пиков на `Rmin`, `dt`, скорость/направление изменения Rs и фазу. Различить ошибку численной/измерительной реализации от режима, где текущий алгоритм не находит валидный sync в допустимое время.
4. Уточнить семантику одного scalar ratio. Документ сейчас задаёт общий интервал, допустимый для всех дендритов; он не гарантирует, что каждый tip может пройти весь диапазон `Rm_i/q … Rm_i*q`. Сначала рассчитать фактическое сужение и связать его с Rmax отказами. Только если оно ограничивает кейсы, решить, соответствует ли требованию пер-tip диапазон.
5. Если требование — полный индивидуальный диапазон для каждого tip, подготовить отдельную C++-правку: helper границ по индексу `Rm_i/q` и `Rm_i*q`; использовать его в инициализации, обновлении, clamp и проверках границ; общие публичные `ResistanceMin/Max` определить как наблюдаемые envelope/diagnostic state. Реализовать и проверить Classic и Branch отдельно. Если договорённость — единый общий Rs-интервал для всех tips, оставить scalar-модель и документировать фактический `ratio_max_i`.
6. Не повышать default `q=1000` на основании одного Rmax. Статья указывает эффективный диапазон около `[0.1, 10]`, а проверяемый диапазон `[0.001, 1000]` существенно шире. Если трасса покажет, что именно верхнего диапазона не хватает, сначала выполнить ограниченный симметричный sweep одного ratio (например `100`, `1000`, `3000`) на двух явных Rmax-кейсах и одном PASS-регрессионном контроле. Поскольку один параметр меняет также reciprocal lower bound и диапазон старта, в отчёте явно обозначить этот sweep как совместное изменение двух краёв, не как изолированную проверку Rmax.
7. Структурные режимы проверять отдельно: вычисляемые параметрические границы не должны применяться там, где Rs вообще не настраивается.

## Шаг 5. Решение об исправлениях

Исправлять только воспроизведённые дефекты, минимальным изменением и отдельным C++-тестом.

| Диагностический результат | Действие |
|---|---|
| Monitor/report сопоставил запуск со старым bundle или неверно прочитал десятичные значения | Исправить только Bin-анализатор/manifest; повторно построить отчёт из первичных артефактов |
| Reset потерял границы/ratio, использовал устаревший topology или C++ state не отражает текущий лимит | Минимально исправить соответствующий Classic/Branch код; тестировать reset, тип режима, topology и наблюдаемое State |
| Rmax отказ записан неверно, произошёл до реального достижения лимита или при неверных EOL/валидности | Исправить C++ условие отказа; добавить тест на сторону/границу допуска и валидность пика |
| Направление/Clamp Rmin/Rmax неверны для валидного измерения | Исправить update в соответствующем тренере; отдельные тесты overshoot/undershoot и обеих границ |
| Branch меняет неактивную ветвь/нарушает reverse-order или reset anchor | Исправить только Branch runtime и добавить тест с несколькими ветвями/активным импульсом |
| Тренер корректно доходит до Rmax и отказывает, либо `Need=1` при законченных лимитах без нарушения контракта | Не маскировать отказ. Зафиксировать как ограничение алгоритма/протокола в проверенных условиях; дальнейшее улучшение алгоритма — отдельная задача |
| `Need=0`, но качество/детекция не проходят | Разбирать отдельно post-training gate и конфигурацию; не менять условие сходимости из-за качества |

Запрещённые средства «исправления»: перенос алгоритма обучения в Python/bash, включение W3 для превращения отказа в PASS, ослабление acceptance thresholds, изменение структуры во время параметрического опыта без явного контракта.

## Шаг 6. C++-проверки, удалённая сборка и повтор

Перед целевой правкой составить таблицу проверок к затронутому контракту. Включить случаи из исходного аудита, относящиеся к изменённой ветви:

- epsilon и границы допуска; валидный/невалидный peak и EOL;
- направление TipR при overshoot/undershoot и Rmin/Rmax;
- холодная инициализация Rs от Rm, вычисление/очистка границ в параметрическом и структурном режимах;
- корректное применение изменения длины, когда оно разрешено текущей политикой, без включения W3 в исследуемый baseline;
- Branch active-pulse, reverse-order, несколько ветвей и reference anchor после reset.

Собрать Console на сервере из зафиксированных root/Bin/PulseLib SHAs и записать SHA256 бинарника, compiler/toolchain, команды и лог. В первую очередь повторить только затронутые кейсы и PASS-контроли из восьмёрки. Для каждой правки сравнить C++ audit до/после. Полный full49 запускать после прохождения целевых проверок и подтверждения исправленных отчётов; использовать отдельный `matrix_id`, не удалять предыдущий RCS/bundles, запускать 6–8 изолированных Console по capacity gate.

**Критерий завершения:** таблица `case → факты из первичного audit → training status → separability → detection → категория → C++/Bin решение`; каждое заявление о дефекте связано с воспроизводимой трассой и проверкой; неизвестное остаётся `insufficient_data`; алгоритмическая невозможность не утверждается на основании конечных запусков.
