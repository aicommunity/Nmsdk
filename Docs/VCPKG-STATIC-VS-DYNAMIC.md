# Статическая и динамическая линковка зависимостей vcpkg (Boost, curl и др.)

## Текущее состояние (всё динамически)

- В проекте используется **динамическая** линковка зависимостей vcpkg: triplet `x64-windows` (VS2022) и `x64-windows-v142` (VS2019, overlay).
- Boost, libcurl, glog, opencv, python3, zlib и транзитивные зависимости поставляются как **DLL**; они копируются в `Bin\Platform\Win` скриптом `DeployVcpkgDlls.cmake`.
- Qt остаётся shared (DLL): из C:\Qt или из vcpkg.

## Можно ли собрать Boost и libcurl (и др.) статически?

Да. В vcpkg для этого используется triplet со статической линковкой библиотек и **динамическим CRT** (рекомендуемый вариант для развёртывания под Windows):

- **VCPKG_LIBRARY_LINKAGE** = `static` — библиотеки (boost, curl, zlib, glog и т.д.) собираются как `.lib` и линкуются в exe.
- **VCPKG_CRT_LINKAGE** = `dynamic` — CRT по-прежнему через `/MD` (DLL), совместимо с Qt и с VC++ Redistributable.

Стандартный triplet vcpkg: **x64-windows-static-md** (его можно взять за основу для overlay).

## Плюсы статической линковки (boost, curl, glog, zlib, opencv)

- **Меньше DLL в развёртывании** — не нужно копировать `boost_*.dll`, `libcurl.dll`, `libssl`, `libcrypto`, `zlib1.dll`, `gflags.dll`, `glog.dll` и транзитивы; в `Bin\Platform\Win` остаются по сути только Qt, CRT и при необходимости opencv/python, если они останутся shared.
- **Один набор CRT** — весь код приложения и статически слинкованных библиотек использует один и тот же CRT в одном процессе; нет смешения версий DLL разных библиотек.
- **Проще установщик и перенос** — меньше файлов, меньше зависимостей от версий DLL на целевой машине.
- **Нет подмены DLL** — сторонние DLL тех же имён не перехватят вызовы.

## Минусы статической линковки

- **Размер exe** — увеличивается за счёт кода boost, curl и др. внутри исполняемого файла.
- **Время сборки vcpkg** — статическая сборка многих портов часто дольше и тяжелее.
- **Ограничения по портам**:
  - **python3** в vcpkg на Windows нередко предполагает или требует DLL (расширения, загрузчик); при полностью статическом triplet сборка или использование python3 могут быть проблемными. В манифесте `python3` сейчас в обязательных зависимостях — при переходе на static triplet может понадобиться сделать его опциональным (feature) или принять, что под static сборка потребует доработок/проверки.
  - **opencv** в целом поддерживает статическую сборку, но с частью опций (например, FFmpeg, Python-биндинги) бывают лицензионные или технические нюансы; для базового набора модулей статика обычно допустима.
- **Обновление библиотек** — при обновлении boost/curl и т.д. нужно пересобирать приложение (нет «подмены DLL» без пересборки).

## Варианты

### Вариант 1: Оставить как есть (всё dynamic)

- Текущие triplets: `x64-windows`, `x64-windows-v142`.
- Плюсы: максимальная совместимость со всеми портами (python3, opencv, Qt из vcpkg), без изменений в сборке.
- Минусы: много DLL в `Bin\Platform\Win`, нужно копировать и поставлять их (в т.ч. CRT при необходимости).

### Вариант 2: Статическая линковка для «ядра» (boost, curl, glog, zlib) через static-md triplet

- Добавить в overlay triplets, по аналогии с `x64-windows-v142.cmake`:
  - **x64-windows-v142-static-md.cmake** — для пресетов VS2019 (localqt): toolset v142, `VCPKG_LIBRARY_LINKAGE static`, `VCPKG_CRT_LINKAGE dynamic`.
  - **x64-windows-static-md.cmake** (или скопировать стандартный и при необходимости добавить overlay) — для пресетов VS2022 (vcpkgqt), если нужна статика и там.
- В пресетах (например, только для localqt или для всех) задать `VCPKG_TARGET_TRIPLET` = `x64-windows-v142-static-md` / `x64-windows-static-md`.
- Итог: boost, curl, glog, zlib (и по возможности opencv) статически линкуются в exe; Qt и при необходимости python/opencv остаются DLL. В `Bin\Platform\Win` остаётся минимум DLL; `DeployVcpkgDlls` по-прежнему копирует то, что есть в `vcpkg_installed/.../bin` (главным образом Qt при vcpkgqt, плюс то, что порты оставят в bin при static).
- Нужно: проверить сборку с **python3** и **opencv** под static triplet; при неустранимых проблемах — убрать python3 из обязательных зависимостей для этой конфигурации или оставить только dynamic-пресеты для сценариев с Python.

### Вариант 3: Два набора пресетов — «dynamic» и «static»

- Оставить текущие пресеты с dynamic triplet (как сейчас).
- Добавить отдельные пресеты, например:
  - `win-vs2019-release-localqt-static` (triplet `x64-windows-v142-static-md`),
  - при желании аналог для VS2022 + vcpkgqt с `x64-windows-static-md`.
- Пользователь выбирает: либо «много DLL, всё совместимо» (dynamic), либо «меньше DLL, статическое ядро» (static). Сборка и развёртывание тогда явно разделены по сценарию.

## Рекомендация

- **Желательно попробовать Вариант 2** (статическое ядро для localqt): добавить overlay triplet `x64-windows-v142-static-md`, переключить пресеты **win-vs2019-*-localqt** на этот triplet и проверить полную сборку. Если python3 или opencv не соберутся/не заработают — оформить их как опциональные (feature) для static-сборки или оставить только dynamic-пресеты для сценариев с Python.
- **Qt** при этом остаётся shared (C:\Qt или vcpkg) — так и задумано; статика только для boost, curl, glog, zlib и по возможности opencv.
- **DeployVcpkgDlls**: при статическом triplet каталог `vcpkg_installed/.../bin` может быть пустым или содержать только Qt/другие shared — скрипт уже это переносит; падать при отсутствии DLL не должен (достаточно не копировать лишнее). При необходимости можно явно разрешить отсутствие каталога `bin` (предупреждение вместо ошибки), если такой случай появится.

Если нужно, можно следующим шагом добавить конкретные файлы overlay triplets и правки в `CMakePresets.json` под выбранный вариант (2 или 3).
