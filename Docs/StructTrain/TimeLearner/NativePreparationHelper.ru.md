# Подготовка native-проверок: один типизированный источник

Расширение repo-module schema2 прошло30/30 metadata tests на M40: исходные24 и шесть новых проверок module/arguments/source provenance. Source `8bf773d4ce6f3b23d79796a8536e5c54d526341a`, evidence `e70610024aeb18662417bbf18d2b6fce430282ea`, [независимая квитанция](NativePreparation30M40A2IndependentVerification.json). Проверены реальные CLI/JUnit, исходные байты fixtures, закрытие единственной owned group и освобождение lease. SDK, C++ и модель этим заданием не запускались. Schema2 пригодна для подготовки maintained worker; сам worker и полный248 cohort требуют отдельной приёмки.

Модуль `Scripts/StructTrain/TimeLearner/native_preparation.py` проверяет перенос метаданных из [разбора подготовки](NativePreparationMetadataReview-20261108.ru.md). На M40 прошли24/24 адресных metadata tests без пропусков. [Независимая квитанция](NativePreparation24M40A1IndependentVerification.json) сверила626 Scripts blobs,435 Python files,два fixtures,реальный CLI/unittest output и закрытие owned group. Source Root `5ebbdfb380fcd8362f534211252bdf2efb4a03e9`, evidence `4ff9bd1a6f157562fdc61d22991a10a6dc00af70`. Модуль не запускает процессы, не обновляет исходники и не меняет registry/lease; приёмка полного runner остаётся отдельной задачей.

`prepare_native_checks` сам вызывает штатный `capture_git_case_inventory`: получает actual clean Git closure, читает канонические Git blobs и проверяет рабочие байты выбранных источников. C++/Git parser не дублируется. Явный список выбранных test IDs должен быть подмножеством полученного inventory. Flatten runplan обязан точно совпасть с этим списком, включая порядок, уникальность и полноту; именованные partitions обязаны покрывать его без повторов с правильными counts. Поэтому compiled universe и реально выбранные cases остаются разными величинами.

Для новых maintained frontends `claims=None` создаёт root/Pulse/TU/count/order поля непосредственно из единственного capture. Если frontend ещё содержит копии текущих metadata, он передаёт их в `claims`: root/Pulse, inventory, runplan, partitions и counts сверяются полностью. Дополнительные именованные root/Pulse/source SHA claims проверяются тем же capture; неизвестные активные поля запрещены. Вложенный archive hash нельзя незаметно оставить от другого commit. Исторические сведения передаются только в отдельном `historical`; их старые SHA/counts не обновляются вместе с active declaration.

`claims=None` не анализирует произвольный worker body и не доказывает отсутствие старых inline constants. Для full248 maintained worker обязан читать current/inventory/runplan из сериализованного canonical spec либо передавать на проверку именно фактически сериализуемые поля своего frontend. Извлечение embedded bytes не подтверждает значения metadata внутри Python-программы. Подключение helper к выполнению остаётся отдельной обязательной проверкой.

Предыдущие binding records сравниваются с сохранёнными исходными JSON bytes. Проверяются их content SHA256/integrity digest, schema и полное равенство записей; исходные bytes входят в spec как base64 с размером и SHA256. Это не цифровая подпись и не доказательство текущего состояния процессов. Свежую kernel closure по-прежнему проверяет штатный `contained_process` перед запуском, а recovery/lease API модуль не ослабляет.

Первый выпуск extractor поддерживает только явно объявленный POSIX supervisor в UTF-8/LF. Он статически извлекает ровно один literal вызов `WORKER.write_text(..., encoding='utf-8')` либо `WORKER.write_bytes(...)`. Dynamic/multiple/неизвестные writers и кодировки отклоняются. Никакой Python-код не исполняется. Default POSIX newline либо явные `newline=''`/`'\n'` сохраняют LF; Windows supervisor здесь не поддерживается. Это проверка embedded-byte consistency, а не доказательство исполнения ветви, пути назначения или actual worker file. Launcher обязан сверить реальные записанные worker bytes до запуска.

Для maintained repo module предусмотрен отдельный schema2 `prepare_native_module_checks`. Schema1/literal режим и его поля сохраняются. Schema2 не содержит worker/supervisor/embedded-поля и не требует фиктивной записи неиспользуемого body. `execution` имеет ровно `mode='repo_module'`, dotted `module` внутри Scripts.StructTrain.TimeLearner, типизированные строковые `arguments` и `source={commit,path,git_blob,bytes,sha256}`. `_git_blob` и `_frozen` читают actual Git blob и физический module file, затем повторно проверяются closure/HEAD. `module_source_bytes_verified_at_preparation=true` относится только к этому чтению; `loaded_module_bytes_verified=false` не разрешает считать модуль загруженным либо выполненным. Реальный процесс под lease отдельно проверяет actual source/module files. Module/args не исполняются при подготовке.

Preparer и SDK worker запускаются разными Python-процессами: смена sys.path не делает безопасным смешивание уже закэшированного Scripts.* namespace. Tool-root подготовки и SDK-root с native_gate/runtime фиксируются раздельно, а actual module files проверяются в своём процессе.

`serialize_preparation` сохраняет декларативный JSON с content SHA256 и запрещает подменять scope-флаги на compilation/kernel/assertion/scientific PASS. После подготовки все потребители читают counts/identity из этого JSON; глобальные замены строк, чисел и opaque identifiers в script bodies не применяются.

Адресные Linux metadata tests используют actual Git objects Rootcc23 и исходные bytes eaa/e89: copied root540, nested05f вместо a35, три реально обнаруженных binding corruption, неверные counts/order и embedded-byte mismatch. Fixtures не запускают исторические scripts и не рассчитывают нейрон. Source closure в этих unit fixtures — сохранённая actual metadata, а не имитация живого Environment; Git blobs и рабочие файлы читаются production-путём. Исполняемые компоненты, graph/dynamics, kernel closure и научные критерии этим набором не подтверждаются.
