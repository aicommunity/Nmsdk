# Объём артефактов и варианты дальнейшего хранения

Проверка по вопросу пользователя о росте Git. Пользователь выбрал компактный
Git: сжатые первичные данные, модели, метрики и выбранные рисунки; полные
отчёты воспроизводятся и хранятся как кэш M40. Это заменяет прежнее требование
хранить все производные изображения в source Git. Опубликованную историю не
переписывать и уникальные первичные данные не удалять.

## Измеренный объём

Измерения получены на M40 непосредственно из Git trees через `ls-tree -r -l`
и `cat-file --batch-check`, без пересчёта моделей или изменения артефактов.

| Снимок | Файлов | Логический размер |
|---|---:|---:|
| Reports/StructTrain/TimeLearner в root fb01871cf2158ece735ab45e148fc20fc33594cd | 91066 | 1731056943 bytes |
| Новый полный Elder report, commit 03d02cd5abb6923274fb83cd17361cc591a3666f | 12955 | 685367382 bytes |
| Новый полный M40 report, commit bd79b0d31724f7230d658bcbc70bccdb5a0bdb25 | 12955 | 685366790 bytes |

Таким образом, прежний снимок и два новых каталога вместе представляют около
3.10 GB / 116976 файлов в рабочих деревьях. Это не размер `.git`, не полный
объём всей истории и не фактический прирост переданных по сети данных.

У каждого нового пакета около 472 MB приходится на PNG, 65 MB на SVG,
59 MB на PDF, 69 MB на JSON и 18 MB на CSV. Примерно 87% логического объёма
занимают три формата производных изображений. Генератор создаёт overview,
последовательные zoom и дополнительные detail views для всех trial/soma пар;
тестовые gates также повторно сохраняли большие графические наборы.

В двух новых пакетах вместе 18733 уникальных blob SHA с суммарным содержимым
840353209 bytes. Их текущее object storage занимает 483322629 bytes без
commit/tree objects. Это не доказанный прирост `.git`: часть blob могла уже
существовать в прежней истории, а repack меняет способ хранения и delta.
Идентичные файлы Git переиспользует, но это не делает бесплатными новые PNG
или SVG/PDF с изменившимися metadata/идентификаторами.

## Причина и варианты

Требование Git-only синхронизации и прямой пункт плана о публикации images/
indices/manifest были применены ко всем производным форматам каждого gate.
Такое исполнение даёт переносимые отчёты, но создаёт избыточный постоянный
объём. Читаемый масштаб графиков сохраняется при любом из вариантов ниже;
он не требует хранения каждой производной картинки в истории исходников.

1. Компактный source Git: lossless compressed primary traces, model/config,
   events, numeric metrics, manifests, renderer version и ограниченный набор
   контрольных figures. Полные reports воспроизводятся из этих данных и
   кешируются на M40. Для научной повторной проверки primary остаются в Git;
   отсутствие cache не означает утрату измерений. Потребуются extraction/
   regeneration CLI, readback hashes и новая проверка self-contained bundle.
2. Отдельный Git результатов: полный отчёт и данные хранятся в отдельном
   репозитории; source Git содержит точные commit/path/checksum references.
   Это сохраняет Git-only синхронизацию, но требует отдельной проверки
   доступности artifact closure. Рост переносится из исходников в results Git.
3. Сохранить нынешнее полное хранение в source Git с осознанным ростом объёма.

Пользователь явно выбрал вариант 1. Это не основание ослабить полноту raw evidence или отменить
графики всех паттернов. Удаление уже tracked рисунков из нового commit уменьшит
checkout, но само по себе не удалит их blob из истории. Очистка опубликованной
истории — отдельная операция; она здесь не разрешена и не выполнялась.

Получение полного Elder branch в основном локальном дереве было остановлено
после выбора новой политики вместе с ожидавшим после него merge. Остановлено
только подтверждённое дерево собственных процессов fetch/queued merge;
HEAD остался 7bde5dc4515afcf3e49d6165482e26f7c2cb233d. Большие опубликованные
ветки 03d02cd/bd79b0d сохраняются в истории; они не объединены в develop.
