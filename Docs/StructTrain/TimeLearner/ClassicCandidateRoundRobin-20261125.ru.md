# Кандидат циклического поиска входов Classic

## Причина и статус

В завершённой попытке Classic политики4 найдено25 кандидатных записей входа0,
9 входа1 и ни одной входа2. Конечная модель даёт TP1/FP1/TN13 на15 разных
паттернах двух наборов, но отдельная проверка сдвига третьего импульса дала
TP1/FP7/TN0. Это измеренная причина исследовать распределение поиска между
входами, без замены собственной амплитудной цели, закреплённой вершины или
допусков. [Научные данные и пределы](ClassicThirdPulseSensitivityResults-20261124.ru.md).

На отдельной ветке подготовлен `ClassicCandidateRoundRobin` ядра контроллера.
Это **не принятый этап**, не выбранный действующими заданиями режим и не новый
научный результат. Его компиляционные и физические проверки ещё требуются.
Механическое выделение состояния сохранено отдельным предыдущим коммитом
и имеет самостоятельную очередь A/B-проверки.

## Изменение алгоритма

При M входных импульсах обучаются входы0,…,M−2; M−1 остаётся опорным.
Каждому незавершённому входу по кругу даётся объявленное число полных кандидатов:
новая пара anchor/input, штатная пачка и все объявленные повторы.
Переключение внутри незавершённой пробы запрещено. Это не обещание равного
времени CPU: разные длины графа имеют разную вычислительную стоимость.

Для каждого входа сохраняются конечные курсоры и израсходованный кандидатный
лимит. Пробы, edits, invalid и N0-предложения длины остаются общими для попытки.
Следующий sweep возможен только по прежней политике после отрицательной
полной финальной проверки.

После любого intervening edit меняется epoch. При возврате к входу локальные
остатки, brackets и effective Rs domains инвалидируются, даже если L/Ns/Rs
в итоге совпали: мог измениться физический binding. История сохраняет свои
первоначальные revisions. Старый выбранный вариант может быть только
предложением собственных координат, предъявляемым заново на текущем фоне.
Полные параметры и C остальных входов при этом не откатываются.

Поправки C восстанавливаются только для собственного независимого пути,
включая dormant-сегменты. Требования к C0 origin, policy и сохранности истории
не ослаблены. Независимый fresh final gate проверяет все входы окончательной
модели; локальные успехи и завершённый процесс его не заменяют.

## Совместимость и ограничения

По умолчанию остаётся `Sequential`, включая прежние JSON и configured learner.
Первый кандидат доступен только конфигурации C++-ядра и закрыт для native
admission/export. Следующий, ещё не проверенный кандидат подключает общую
версионированную декларацию к cold/runtime/summary и Python-читателям.
Branch сохраняет обратный порядок и не принимает Classic-only выбор.

Квант полного кандидата отличается от legacy-переключения по отдельным пачкам.
Его эквивалентность не заявляется. Нужно проверить кодеки и effective readback,
пересобрать SDK, выполнить native lifecycle/storage/measurement проверки,
затем сравнить холодные обучения в одинаковых условиях. Действующие Train
8/24 и контроль0 продолжаются на своих неизменённых сборках.

## Подготовленная проверка

Отдельный target `Test_PulseLib_ClassicInputRoundRobin` компилирует полные
production translation units; тела функций не копируются. Подготовлены14
контролируемых decision-сценариев: M=1/2/4/6, нормализации Ns/Rs, закрытие пары и повторов,
общий нечётный бюджет, fresh final rejection, новый sweep, новые Rs domains,
сохранность других входов/C, aggregate seed limit и external stop.
Такие наблюдения проверяют решения контроллера, а не физику кабеля.

Дополнительно требуется прежний полный набор157 случаев до/после при
`Sequential` без ожидаемых baseline-отказов. Успех этих проверок ещё не
получен. После них остаются native-кодеки, физические эксперименты и общая
приёмка исходного плана0–12.

[Владельцы состояния и псевдокод PulseLib](../../../Libraries/Nmsdk-PulseLib/Docs/TimeLearner/InputSearchStateOwnership.ru.md).

На M40 созданы отдельные исходные деревья для нового кандидата и baseline.
Заявлены две проверки:157 случаев на каждой стороне при Sequential и14
адресных случаев нового выбора. Git controls и bundle обоих источников

успешного закрытия самостоятельной проверки механического рефакторинга;
та, в свою очередь, ждёт научную галерею и независимое восстановление данных.

## Следующий кандидат: сохранение режима и размер визита

В отдельном изменении добавлены общий C++-кодек `InputTraversalJson.h` и
Python-читатель `input_traversal.py`. В `search` cold/runtime-документа и
`configuration` summary сохраняется один и тот же объект:

```json
"input_traversal": {
  "kind": "timelearner_input_traversal",
  "schema_version": 1,
  "policy": "classic_candidate_round_robin",
  "candidates_per_visit": 3,
  "maximum_seed_elements": 131072
}
```

Отсутствие поля сохраняет Sequential. Все пять полей новой декларации
обязательны; неизвестные версии, лишние поля, bool/count ошибки и Branch
отклоняются. Декларация сопоставляется с фактическим summary. Текущий warm
runtime plan сохраняет свой размер визита, без подстановки cold-значения.
Производственный сериализатор ConditionSpec сохраняет этот фактор целиком;
подготовлен контроль его fingerprint и перестановки ключей.

Квант1 может лишать часть входов истории трёх свежих длин после изменения
фона. Прогноз `ProposeMeasuredLength` использует минимум3 такие точки.
Явный квант3 даёт возможность измерить их до переключения. Добавлен
контролируемый сравнительный сценарий1/3 с одинаковыми физическими откликами
и общими бюджетами. Прогноз остаётся предложением: новые пробы и финальная
проверка обязательны. Разные C-контексты должны иметь совместимую физику;
сам квант3 сходимость не гарантирует.

Подготовлены18 случаев decision/codec и3 случая native-деклараций:
scalar/composite/candidate/terminal envelopes, обе нормализации, C Off/On,
warm quantum и recovery. Результатов исполнения этого следующего кандидата
ещё нет в полном объёме. На Elder прошли11/11 Python-проверок декларации;
production C++-набор действительно скомпилирован и выполнил18 случаев,
из которых17 прошли. Один отказ обнаружил ошибочную предпосылку fixture:
при одинаковом отклике L=1/2 нельзя требовать окончательного L=2 вопреки
штатной меньшей стоимости изменения. Fixture теперь явно задаёт измеренное
улучшение L=2 на каждом из трёх путей, сохраняя отрицательный исход обучения
и проверку отсутствия отката чужих параметров. Повтор ещё требуется.
Исходный отказ и две ошибки подготовки сохранены отдельно; прежний
production-алгоритм ради этого отказа не менялся.
Очередь предыдущего кандидата14 остаётся неизменной и не проверяет
эти новые изменения. Свежий SDK и физические сравнения ещё требуются.
