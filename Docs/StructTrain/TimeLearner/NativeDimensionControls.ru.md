# Физические контроли размерности и финальной верификации

Это адресный контроль этапов 3–7, а не закрытие полной матрицы и не эксперимент
по качеству классификации. Предыдущие двухвходовые N0-прогоны были отрицательными;
необходимо было отдельно проверить достижимый положительный финальный gate и
обработку количества входов, включая больше четырёх.

## Постановка

Production CLI `train` выполняет холодное обучение реальных компонентов
Classic/Branch, N0/N1, при N=1/2/4/5 и 2000 Гц. Каждый запуск создаёт собственный
процесс Console. Используются определения storage-профилей из прежних явно
указанных job artifacts; сохранённые references и learned graph не устанавливаются
в learner. Builder создаёт объявленную начальную структуру штатным путём.

Исходники подготовителя/численных запусков:
`ce2038fa8894f7959cd86f5f97c494f06be4b0ce`; reader:
`2e519f6dcd69e73f941e147d69785db903f0ebf2`. Исполняемые файлы и их сборочные
источники остаются ранее проверенными dedicated N0 runtime; runtime manifests
входят в proof. Новый Python commit не приписывается исходникам Console.

Все подключения имеют L=1, Ns=1 и индивидуальное исходное Rs=86 МОм.
Допустимые диапазоны L/Ns/Rs фиксируются на этих значениях. Для Classic
выделяется N отдельных путей; для Branch — один общий кабель с совпадающими
подключениями. Эта особенность Branch явно ограничивает покрытие: контроль не
проверяет все разные attach positions и их рост.

Первый ISI равен 0.01 с, последующие — 0.08 с. Окно пробы:
`0.18 + 0.08*(N-1)` с; ёмкость записи рассчитывается по частоте. Пороговые
допуски не ослабляются: amplitude absolute `1e-5`, relative `0`, sync `0.02` с,
minimum amplitude `1e-6`. Никакие пики не создаются аналитически.

* N=1 проверяет тождественную сходимость: геометрия не меняется, но требуется
  новая физическая проба финальной верификации после capture. Это положительный
  контроль gate, а не доказательство эффективности изменения морфологии.
* N=2/4/5 проверяют размерность и отрицательный исход при фиксированной
  геометрии и разнесённых импульсах. `SearchUnresolved` не означает
  `PhysicalInfeasible` для более широкого пространства параметров.

Job schema 1 означает bare Train без live finalization, PostTune и калибровки;
это по-прежнему новый native контроллер V2, а не legacy алгоритм V1.
Распознавание/frozen evaluation в этот контроль не включены.

## Проверки и фактическое состояние

На Elder завершены 16/16 запусков: четыре N=1 — `Exact`, остальные двенадцать —
`SearchUnresolved`. Два читательских набора по 4 теста прошли: целостность
production artifacts; полный набор case IDs; свежие distinct `/verify/` trials
для каждого входа; сохранение исходных допусков/profiles; фактическая размерность
baseline и каждой строки CSV. У Classic N=5 проверен пятый канал сомы, у Branch
во всех размерностях записывается одна общая сома.

Первичные данные опубликованы commit
`9ae741dac27073f82efebba7cc62b4749d9ad413`, каталог
`Reports/StructTrain/TimeLearner/s07-native-dimension-normal-a1`:
715 файлов, 87 219 737 исходных байт, lossless archive 956 784 байта.
Архив восстановлен на M40 только через Git с проверкой каждого member SHA.

На M40 четыре одновходовых ASan case также завершились `Exact`; pilot reader
4/4. Серия N=2/4/5 ещё выполняется; её полного прохождения здесь не заявлено.

## Временные отчёты

Для каждого выполненного Train сохраняются все реальные пробы и каналы сомы.
Production renderer строит кривые SumPotential с наложенными фактическими
входными импульсами: overview и zoom без downsampling, PNG 1920×960,
не менее 8 пикселей на native tick в zoom. Это диагностические Train traces;
им не присваиваются вымышленные target/foil verdict или spike absence.

## Ограничения и следующий шаг

Этот контроль не доказывает успешный поиск, преимущество proposal policy,
независимую классификацию, robustness к порядку/ITI, все physical profiles,
20000 Гц, inhibition, C-trim либо lifecycle growth. Следующая алгоритмическая
проверка должна реально измерить timing-ready изменённую геометрию и соседние Ns,
а не заменить физику управляемым oracle или расширить claim тождественным N=1.

Подэтап остаётся в отдельной feature-ветке до завершения обеих server-серий,
проверки артефактов/отчётов и адресной приёмки. Полные этапы исходного плана
остаются открытыми.
