# Операционные ошибки и численная полнота

Исходная high-threshold проба Classic-6 из commit2194d833 завершилась exit0,
но stderr содержит glog ERROR с `St12system_error Resource temporarily unavailable`.
Чистый повтор из374127ae побитово воспроизвёл данные без stderr. Это показывает,
почему exit status, полнота измерений и операционная диагностика — разные оси.

`operational_diagnostics.py` вводит policy `owned-streams-v1`. После завершения
процесса читаются только его собственные stdout.log/stderr.log, без обхода
общих runtime logs. Сохраняются размеры и SHA256, счётчики и не более16
ограниченных выдержек. Разбор потоковый, строки ограничены64KiB.

* `error`: распознанные glog E/F, traceback или поддерживаемые sanitizer errors.
* `needs_review`: неизвестный stderr, отсутствующий/aliased поток, неверная UTF8,
  слишком длинная строка либо изменение файла во время чтения.
* `clear`: нет распознанных ошибок и неопределённого stderr. Распознанные glog
  warnings учитываются, но не становятся ошибками. Произвольный stdout текст
  со словом ERROR не классифицируется как ошибка автоматически.

Clear означает прохождение этой политики, не доказательство отсутствия всех
возможных ошибок. Неизвестный stderr не объявляется численной ошибкой.

Pidfd и contained runner записывают отдельное `operational_diagnostics`, сохраняя
execution/returncode. Native pipeline не выдаёт положительный audit при error
или needs_review: численные файлы сохраняются, manifest имеет unverified_execution.
Portable auditor повторно читает потоки и сверяет сохранённую диагностику;
подстановка clear или повторное хеширование manifest не заменяет проверку.
Старые process records без поля также проверяются по первичным потокам.
Архивы и исторические критерии не переписываются: старый PASS с ERROR может
быть отклонён новым аудитом, сохраняя исходную запись для исторического чтения.

Тестовые native gates могут намеренно вызывать ошибки отрицательных контролей.
Эта политика не превращает такие gates в научный pipeline и не меняет их JUnit
критерии. Любое исключение из политики для модельных запусков требует отдельной
версии контракта; универсального allow-error флага нет.

Статус: реализация подготовлена; серверные проверки ещё не приняты.
