# Бюджет полного sweep и честный конечный результат

`BoundedTrainingSession` расходует две логические пробы на одного кандидата:
опорный вход и текущий. Для N0 с повторениями это2r проб. По достижении
локального cap текущая реализация дополнительно измеряет восстановленный best.
`FinalVerificationSession` затем измеряет каждый из N входов один раз, включая
опорный. Отдельный anchor на каждый финальный вход не подаётся.

Для N входов, локального cap K и r повторений верхняя оценка одного sweep
при валидных измерениях:

```text
adjustable = N−1
search = 2 r (N−1) K
restore = 2 r (N−1)
final = N
sweep = search + restore + final
```

Захват исходных N references имеет отдельный бюджет. Для N+2 измерителя одна
логическая проба дополнительно требует N+2 штатных native предъявлений.
Recovery, отклонённые edits и задержки между окнами не превращаются в нулевую
стоимость; оценка не гарантирует завершения по model/wall time или сходимость.

Для текущего N4/N1 K16 один sweep требует не более106 search probes в таком
валидном пути:96+6+4. Вместе с четырьмя references это110 логических групп.
Прежнее пояснение «финальных8» было завышением финальной части: актуальный код
подаёт4. При maximum_sweeps4 верхняя оценка424 search probes уже превышает
объявленные128. После отрицательной первой финальной проверки контроллер может
начать второй sweep и исчерпать бюджет внутри него. Guard Pulse5d запрещает
новый edit после последней пробы, но не восстанавливает лучший полный граф.

## Следующий явный контроль

Подготовлен production-инструмент `Scripts.StructTrain.TimeLearner.cold_budget`.
Он принимает подписанный **cold Train job**, сохраняет всю физическую модель,
storage-профили, topological/routing declarations, окна, stimulus, optional
modes Off и допуски. Изменяет только run identity и явно названные бюджеты,
заново подписывает job и выдаёт проверяемый declaration. Запуска при import нет.

```text
python -m Scripts.StructTrain.TimeLearner.cold_budget \
  --template <immutable-cold-job.json> --run-id <new-run-id> \
  --candidates-per-input 24 --maximum-probes 160 \
  --model-seconds 10000 --output <fresh-output>
```

Выход: job.json и declaration.json. Источник читается как замороженный файл
с ограничением64MiB. Неизвестная/повреждённая схема, недостаточный логический
бюджет, недостаточные group/native/sample capacities либо заведомо слишком
короткое суммарное окно отвергаются до создания output. Secondary limits не
увеличиваются автоматически. Конфигурация всё равно требует native effective
preflight на сервере; утилита не подтверждает наличие образов или устойчивость.

N4/N1 K24 требует154 search probes:144+6+4. Capture добавляет4, итого158
валидных групп /948 native предъявлений. Бюджет160 оставляет небольшой запас
на отказы, но не обещает успешной recovery. K24 выбран потому, что в предыдущем
Branch локальная точность входа2 получена только на24-м кандидате. Единственный
sweep, если обход дойдёт до финальной проверки, заканчивается на этом этапе
вместо начала следующего. До него всё ещё возможна честная остановка по времени,
invalid observation или другим ограничениям. Это будущий контроль, **не**
результат выполненного эксперимента.
Текущий live cap16 опыт не меняется.

Полное исправление terminal selection остаётся обязательным: хранить/выбирать
полный эффективный граф и индивидуальные параметры, восстанавливать штатным
native импортом на законной границе, проверять readback и не переносить на
новый epoch старый Exact. Этот preparer не подменяет такое исправление.

Шесть контрактов проверяют обе топологии, N0/N1, повторения, native secondary
limits, неподменяемость модели/допусков, подпись и реальный CLI с замороженным
