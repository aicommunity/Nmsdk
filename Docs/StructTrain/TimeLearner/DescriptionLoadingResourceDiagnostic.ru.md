# Ресурсная диагностика при загрузке описаний Rdk

В Git-primary `2194d833df5910207dfc8cf2895f8b11608db2f8` одна из14
high-threshold проб, `a2/worker/corpus/Classic-6` (только импульс3), содержит
`St12system_error Resource temporarily unavailable` в stderr и ERROR/INFO logs.
Остальные15 исходных/повторно используемых process records не содержат stderr.

Процесс завершился с exit0; прежний pipeline принял полное окно CSV,
semantic model identity, импорт и восстановление target. Это не доказывает
безвредность зарегистрированного исключения. Научная приёмка Classic-6
остаётся предварительной до адресного повтора и установления области ошибки.
Исходный пакет не переписывается; его boolean acceptance не подменяет эту
дополнительную проверку исполнения.

В Rdk10e9d05a обнаружены два неограниченных запуска потоков при чтении XML:
`URuntimeLibrary::LoadCompDescriptions` и `UStorage::LoadClassesDescription`.
Они создают `std::async(std::launch::async)` для каждого файла до сбора
результатов. При исчерпании slots исключение возникает вне lambda обработчика.
Эти места являются подтверждённым риском; точный источник старого исключения
не установлен, поскольку stack trace не сохранён.

Rdk-ветка от develop содержит исправление b3438347: `launch::deferred`, прежние
порядок чтения/регистрации и обработка XML, без дополнительных потоков.
Lifecycle и bool Build/Calculate/Reset не меняются. Root-ветка также создана
от develop; необходимые диагностические зависимости объединены --no-ff.

Подготовлен target `Test_Rdk_RuntimeDescriptions`, использующий настоящую
Rdk библиотеку. Он сверяет порядок/сериализацию32 XML и выполняет тот же путь
без свободных slots в собственной ограниченной cgroup. Fault включается
только при kernel-enforced 8–32 tasks; targeted gate требует обе проверки
без skipped и actual loaded-file capture. Ограничение действует на отдельную
группу задания, а не на пользователя или сервер.

Приёмка ещё не выполнена. Требуются before/after gate, проверка storage/profile
fixtures и чистый повтор Classic-6 с полной сверкой всех четырёх soma traces,
реальных stimulus samples и fingerprints. Ошибку первоначального запуска
сохранять отдельно; исчезновение записи в одном повторе не является
самостоятельным доказательством исправления всего загрузчика.

В runner остаётся открыто требование: operational ERROR должен учитываться
отдельно от exit code и численной полноты. Не переносить его в bool Calculate
и не считать любое предупреждение доказательством численной ошибки.
