# Параметризованные проверки реальных компонентов

## Причина изменения

Сохранённый перечень `--gtest_list_tests` бинарника
`runtime-traversal-native213-m40-dx30/Test_PulseLib_StorageComponents`
содержит 2303 случая. Последний выбранный набор из 213 случаев не является
полной проверкой этого перечня. Из этого различия нельзя заключать, что
остальные случаи никогда не выполнялись в предыдущих сериях.

Версии 1–5 `native_gate` принимают идентификатор `Suite/Case` и заменяют
разделитель на точку при передаче GoogleTest. Параметризованные случаи
содержат дополнительные косые черты в именах набора и случая. Например:

```text
TopologiesAndRates/NativeTimingProperties.RejectNonfiniteWithoutChangingPreviousValue/0
```

Глобальная замена `/` на `.` не сохраняет этот идентификатор.
Это ограничение охвата запускателя; оно само по себе не доказывает дефект
вычислений компонентов или ошибку уже выполненных обычных случаев.

## Версия 6

Новая версия спецификации явно выбирает полное имя GoogleTest `Suite.Case`.
Единственная точка разделяет две части; косые черты внутри каждой части
сохраняются. Маски, отрицательные фильтры, дополнительные разделители,
управляющие символы и дубли запрещены. Декларация содержит точное множество
ожидаемых случаев; JUnit сопоставляется по отдельным `classname` и `name`.
Пропуск, незавершённый случай и несогласованные итоги не дают успешной проверки.
Неуспешное утверждение сохраняется как наблюдаемый отрицательный результат.

Состав полей расширяет версию 5. Обязательны:

- `schema_version: 6` и `cooperative_runtime_capture: true`;
- `expected_test_ids` с полными именами;
- `process_limits` с целыми положительными `memory_bytes` и `tasks`;
- `data_inputs`: явный пустой список либо штатные декларации неизменяемых файлов;
- `artifact_directories`: явная таблица каталогов диагностик либо `{}`;
- прежние привязки исходников, runtime и времени выполнения.

Первый выпуск версии 6 работает на Linux через штатный ограниченный процесс
с проверкой закрытия всей группы и фактически загруженных файлов. Контракты
версий 1–5, включая Windows-версию 4 и обязательные непустые входы версии 5,
сохраняются. Живые научные задания продолжают использовать свои версии кода.

Каталоги диагностик создаются внутри результата текущего запуска. Разрешены
только штатные выходы для проверок профилей, переноса, наблюдений и сброса;
произвольные переменные среды и внешние пути не допускаются. Необъявленные
выходы и управляющие переменные дочерних проверок очищаются на время запуска.
Для проверки совместимости исходный набор сравнения задаётся отдельным
протоколом A/B: отсутствие такого набора не доказывает эквивалентность версий.

Первая серверная проверка формата `parameterized-native-format-eo6` завершила
29 проверок, из которых одна не прошла сравнение со старым перечнем: прежний
сборщик сохранял пробел перед комментариями `GetParam`. Первичный результат
сохраняется. Сборщик переведён на общий разбор; исторический снимок читается
с явным устранением этого пробела только в адаптере его метаданных.

`gtest_full_names.parse_listing` читает фактически сохранённый перечень,
сохраняет имена, отвергает неизвестные строки, пустые или повторные наборы
и дубли случаев. `partition` разбивает полный перечень без потерь и перестановок;
ограничены и число случаев, и длина аргумента в байтах. Снимок перечня и
декларацию каждого запуска хранить вместе с результатом.

## Проверки и границы доказательства

Проверки Python используют реальный сохранённый перечень и завершённый JUnit.
Изменённые копии XML проверяют только поведение читателя: они не считаются
доказательством выполнения параметризованных компонентов.

Приёмка запуска требует реального исполнения выбранных полных имён на
неизменном бинарнике. Проверки графа, сброса, роста, частоты и переноса модели
засчитываются только в пределах утверждений соответствующих исходных тестов.
Полученный PASS не заменяет научные Train/Test, историческое воспроизведение
или приёмку полного этапа плана. Полнота 2303 случаев требует отдельного
сопоставления каждого случая с выполненным запуском и необходимыми данными.

Результаты серверной проверки и внешние первичные архивы добавляются после
фактического завершения; подготовка этой спецификации не является приёмкой.
