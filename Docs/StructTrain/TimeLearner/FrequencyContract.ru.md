# Частоты при создании и замене поддеревьев — TL-016

## Воспроизведённый дефект

`SetGlobalTimeStep` обходил только существующие компоненты. `AddComponent`
передавал детям OwnerTimeStep и видимость свойства TimeStep, но оставлял их
собственную частоту из storage-образа. Поэтому cold Reset/live Build мог
незаметно вернуть часть дерева к 2000 Гц при общем clock=20000.

Новая проверка использует реальный Environment, NModel, оба learner,
NSPNeuronGen, штатный Reset и первый вызов scheduler. До исправления на M40
Classic имел 36/44, Branch 12/14 узлов нейрона с частотой, отличной от 20000.
Оба global controls упали; оба individual controls прошли. Источник root
80450ed и полная closure записаны в pre-test runtime manifest.
Артефакты: `Reports/StructTrain/TimeLearner/s04-frequency-baseline-m40`.

## Исправление на уровне владельца

Rdk `UContainer::AddComponent` после установки Environment применяет частоту
владельца ко всему присоединяемому поддереву, только если Environment объявляет
общий режим. Это выполняется до AAdd/AfterAdd и штатного Init/Reset новых детей.
Контроллер не рассчитывает нейрон повторно и не переписывает его параметры
на каждом тике.

В `UEnvironment::CreateModel` обе перегрузки применяют текущий режим к новой
либо повторно взятой модели. `SetUseIndTimeStepFlag(false)` выравнивает текущее
дерево по частоте корня; true не восстанавливает ранее заменённые значения.

При OpenProject режим устанавливается перед загрузкой модели, а не только
после Init. CloneChannel устанавливает режим до загрузки и применяет общий
clock только при false. Это согласует порядок настройки с новым контрактом;
отдельная полная проверка project open/clone с heterogeneous multirate-графом
ещё требуется и не подменяется проверкой CreateModel.

## Сохранение индивидуальной физики

- При `UseIndTimeStepFlag=true` присоединение сохраняет частоты образов.
- У detached storage-образов нет Environment; их создание/Copy не выравнивает
  индивидуальные частоты. Отдельный native storage fixture проверяет Copy
  root=20000 и child=4000.
- Физические образы не меняются. Общий режим применяется к экземпляру при
  присоединении к модели; остальные параметры каналов/синапсов не затрагиваются.
- Переключать режим и частоту следует между пробами, до штатного Reset/Init.
  Setter сам не сбрасывает динамику и не подменяет lifecycle.
- Default сохраняет свою прежнюю семантику. Вызов Default уже присоединённого
  экземпляра не объявляется способом восстановить обученную модель.

Исторический nominal clock=20000 нельзя ретроспективно считать uniform physics.
Граф с явно включёнными индивидуальными частотами остаётся compatibility.
Для исправленного global-графа ответы могут измениться: это отдельная версия
условий эксперимента, а не доказательство регрессии или научного улучшения.
Августовские визуальные 4/8–6/8 сохраняют прежнюю доказательность.

## Проверки и ограничения

На обоих серверах первоначальная проверка root f3ff145 дала 4/4 controls:
global Classic 44/44 и Branch 14/14 узлов имеют 20000; individual сохраняет
соответственно 36 и 12 отличающихся узлов. Три Rdk fixtures и четыре maintained
CTest suites прошли. Последующий root 59c54e2 добавляет проверку CreateModel
по имени и ID, видимости TimeStep и переключения режима.

Финальный root 59c54e27c89146798d79cd8889b1e76b6c087102 с Rdk
9cb00e640f857b4533518669c8ada01c80efc44e проверен на обоих серверах: пять
адресных integration cases, три Rdk fixtures и 4/4 maintained CTest suites.
Дополнительно два N1 burst controls при общем clock=20000 прошли по три
модельных секунды с фактическими структурными решениями. После роста все 79
узлов Classic и 49 узлов Branch имеют 20000 Гц и Init=true, readback valid.
Raw traces, состояния, binary64 waveform hashes, XML/logs, pre-test manifests
и SHA256 опубликованы в `s04-frequency-final-elder1` и
`s04-frequency-final-m40`. Отдельного ASan прогона этой правки нет.

Это проверка реализации частоты, не завершённый Train и не сертификат
сходимости. Обязательная матрица физических моделей, export/import реального
learner и Controller v2 остаются в работе. Границы дальнейшего приёма должны
опираться на опубликованные runtime manifests, XML/logs и readback после роста.
