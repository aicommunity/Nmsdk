# Повторное открытие реестра worker

В s04-rdk-description-elder-a1 численные задания завершились, но supervisor
не смог освободить резерв: `Reservations(database)` выбирает schema1, тогда
как реестр Elder создан с capacity и schema2. Ошибка и последующее штатное
восстановление сохранены в commit 6117aad55a6d105ad046c1867abc6f4a5a3cb050.

Для уже созданного реестра добавлен `Reservations.open_existing(database)`.
Метод читает сохранённые ограничения, проверяет schema, worker, устройство
файловой системы и набор metadata; затем открывает реестр обычным механизмом.
Он не создаёт отсутствующую базу и не мигрирует старую схему. Для schema3
обязательно явное `managed_units=True`; автоматического включения managed
ownership по содержимому файла нет. Конструктор с явной capacity остаётся
путём создания нового реестра. Несовпадения явной политики по-прежнему запрещены.

Последующие worker/supervisor должны использовать этот метод при повторном
открытии, а не предполагать schema1 или копировать capacity другого сервера.
Он не освобождает lease автоматически, не отменяет проверку закрытия процессов
и не удостоверяет успешное выполнение научного задания.

Проверки используют реальные Linux /proc и SQLite: все три схемы, сохранение
существующего ownership, отсутствующий файл, symlink, неизвестные schema/worker,
лишние metadata, повреждённая capacity, смена устройства и чужая SQLite-база.
До адресного серверного запуска статус изменения — подготовлено.
