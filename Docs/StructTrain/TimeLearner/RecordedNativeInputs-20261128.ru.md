# Записанные входы native-проверок сохранённой модели

## Подтверждённая ошибка постановки

Полный Windows-проход на SDK
`cde0b851a3c156b3c31e6dbadc27b320de9a3884` выявил три случая, которые
пытаются открыть удалённый из Git бинарный fixture по пути относительно
`__FILE__`. В действующем дереве остались корректные descriptor и внешняя
ссылка; самого `learned-state.json.qz` там нет. Первичный JUnit подтверждает
ошибку открытия файла до декодирования и импорта модели:

- `NativeArchiveOwnership.MoveRetainsDecodedPrimaryStorageAndCopyIsIndependent`;
- `NativeClassImageReplay.ActualMembraneCopyAndLoadStages`;
- `NativeClassImageReplay.ClassicActualSavedModelAcrossNativeGraphRelease`.

Это не свидетельства отказа алгоритма импорта. Два отдельных отказа
`NativeImageRestSnapshot` остаются открытыми и этим исправлением не
устраняются. Старые результаты не пересчитываются и не объявляются PASS.

## Исправленный путь данных

Используется существующий production-механизм `native_gate_inputs`:

1. Задание объявляет объект архива как DATA input `classic-package6.qz`.
2. Runner проверяет исходные323020 байт и SHA256, сохраняет descriptor
   и размещает точную копию в собственном `native-inputs`.
3. C++ fixture читает эту копию относительно `TIMELEARNER_EXECUTION_OUTPUT`.
   Он дополнительно проверяет сжатый SHA256, длину qCompress до выделения
   распакованного буфера, все4812359 байт JSON и исходный SHA256.
4. Runner после расчёта проверяет неизменность исходного и staged-файла.

Бинарные данные в source checkout не восстанавливаются. Объявленный
исторический пакет не переписывается, новые defaults не подставляются.
Путь и идентичность приведены в [описании fixture](../../../Tests/Integration/Data/NativeWindowPackage6Classic/README.md).
Linux-контракты5/6 уже поддерживают такие входы. Windows-контракты4/7
пока не поддерживают DATA staging; этот предел сохраняется явно.

## Попутный дефект Windows loader environment

В `native_gate.py` schema7 выбирала `LD_LIBRARY_PATH`, хотя запускает
Windows Job. Теперь schema4 и schema7 одинаково применяют объявленный
runtime `PATH`, `QT_PLUGIN_PATH` и `QT_QPA_PLATFORM`. Linux-контракты
сохраняют свой набор переменных. После запуска исходное окружение
оператора восстанавливается. Две адресные проверки вызывают тот же
селектор и context manager, которыми пользуется production-runner.

## Статус проверки

### Новый Linux C++-проход fr750

Изолированная сборка fr743 завершена на .12: root
`7a54442fb56366e7a374381bb07188fbfe211078`, Pulse
`5f36aebb9bfdef747c04319f3ab065be199de67c`, GCC11.4/Qt6,
отдельный runtime; build занял1566.4 с. Выполнены все9 объявленных
native-проверок без пропусков:8 PASS,1 FAIL. Все три перечисленных выше
replay теперь прошли с явно объявленным DATA input. Source и staged input
проверены до/после; процессы закрыты, реальные библиотеки сохранены.
[Полные110 первичных файлов](../../../Reports/StructTrain/TimeLearner/Progress-20261128/Jump12-recorded-input-native9-fr750.archive.json)
находятся во внешнем архиве; независимая приёмка этого пакета ещё требуется.

Единственный отказ — `RepeatedArchiveAndPoolReuseAt20000`. В трёх циклах
различались только определения Body/LT образов `NPMembraneBio`:
неподключённый нулевой `InputFeedbackSignal` формы1×1 против0×0.
Граф, физическая identity и проверенные массивы входа, времени, канала и
сомы совпали. При2000 Гц roundtrip прошёл. Это не общее доказательство
эквивалентности State и не повод ослабить исходные raw archive сравнения.

Кандидат Pulse `d97b1b5f33244a4a35bd88032c347dc21c8dfdea` приводит
только приватное определение известного native membrane image к пустому
нейтральному буферу. Живой граф, prototype и общие методы Rdk не меняются.
Добавлены отрицательные контроли ненулевого/более широкого буфера,
неверного hash и отличия State самого графа. Новая серверная сборка и
приёмка кандидата пока открыты; старый FAIL сохраняется.

Также прошли schema4 CSV roundtrip и три адресных DATA1/warm-reset
проверки. Linux-результат CSV не подтверждает Windows handle behavior.
Новый источник обучения и завершение полного этапа этим не заявляются.

### Предшествующая проверка и подготовка

На Windows .8 исходник `7a54442fb56366e7a374381bb07188fbfe211078`
прошёл8/8 адресных Python-проверок без пропусков: имена, Windows/Linux
ограничения, применение объявленного окружения и его восстановление.
[Первичные проверки и библиотеки процесса](../../../Reports/StructTrain/TimeLearner/Progress-20261128/Windows8-native-gate-loader-tests-fr736.json)
опубликованы во внешнем архиве. Сами Python-проверки не подтверждают C++;
последующий Linux-проход описан выше. Отдельная Windows-проверка CSV
handle fix и приёмка нового rest-state кандидата ещё нужны. Все неизменные
параметры и методы Rdk сохраняются. Новый исход обучения, научный PASS
и завершение полного этапа плана здесь не заявляются.

Для сборки на .12 используются существующие Git-объекты `/home/user/Nmsdk`
в новых worktree; исходное дерево и старые runtime не переключаются.
Попытка fr739 отвергнута до CMake: связанный Bin worktree унаследовал
относительный `core.worktree` общего Git-конфига и разрешился в каталог
метаданных. Оригинальные восемь деревьев проверены: HEAD, фактический
корень и tracked status сохранены. В новой подготовке fr741 абсолютный
`core.worktree` задан только в собственном worktree-конфиге Bin;
production source-closure прошла без ослабления проверки.

CMake fr741 затем выявил отличие feature flags от прежней проверенной
сборки: по умолчанию включился embedded LLM, для которого отсутствует
`nlohmann/json.hpp`. В fr743 используются точные инструменты и BOOL
feature flags из прежнего CMake cache, включая `RDK_LLM_BUILD_EMBEDDED=OFF`.
Создаётся отдельный build/runtime на уже проверенном источнике fr741.
Оба прежних отказа сохранены. При расчётах на .12 минимум32ГиБ остаётся
обязательным; собственный build останавливается с запасом при36ГиБ.
