# Сопоставимое Classic обучение числом синапсов

Подготавливается новое холодное обучение Classic с M=4. Оно проверяет,
позволяет ли нормализация числом синапсов продвинуть обучение при исходной
физике прежнего опыта с нормализацией сопротивлением. Рабочие результаты
фиксированной прежней модели — TP1/FP2/FN0/TN5 на исходной матрице и
[TP1/FP4/FN0/TN22](ClassicFrozenNewFoilResults-20261121.ru.md) на новой сетке.
Прежний Train исчерпал бюджет; Exact не подтверждён.

## Сохраняемая постановка

Исходники постановки взяты из фактического Elder-запуска
`s11-offline-n4-classic-on-elder-a2/classic-on`: `input/job.json`,
`native/initial-state.json`, `process/runtime.json`. Их исходные байты,
полные пути и SHA256 сохранены отдельно во внешнем архиве M40.
Контейнер43992байта имеет SHA256
`127c1a2859a28521bb440c847f2ddd0d62e89850acd21be56d6911f845a1d185`.
[Ссылка и происхождение](../../../Reports/StructTrain/TimeLearner/MatchedClassicCountTraining-20261121/original-declaration-archive.json).
Это сохранение декларации и начального состояния; полный архив прежнего
длительного Train этим небольшим контейнером не подменяется.

Используется общий `matched_count_job` из `prepared_count_training.py`.
Он сохраняет модель, целевой паттерн, storage-образы, частоту, остальные
режимы, допуски и бюджеты, меняя только идентификатор новой попытки и
разрешённую переменную нормализации. Технический режим N0 означает число
синапсов, а не название топологии. Для обучаемых входов разрешены целые
Nₛ,ᵢ от1 до128, сопротивления фиксируются на фактических исходных значениях.
Последний опорный вход остаётся закреплённым. Исходная цель каждого входа
CapturedPerInput сохраняется.

Достижение Ns128 не означает успеха или неуспеха само по себе. После
закрытия Train необходимо анализировать реальные остатки, ограничения поиска
и итоговый экспорт. Процесс с кодом0 не создаёт сертификата сходимости.

## Проверка исходного физического состояния

Новый Linux-путь находится в корневом пакете, модуль
`Scripts/StructTrain/TimeLearner/linux_count_training.py`. Его математическая
подготовка общая с действующим Windows-опытом Branch; нативный расчёт выполняет
существующая Console. Собственного расчёта нейрона или изменений Rdk lifecycle
в Python нет.

До Train обязательны два настоящих нативных preflight:

1. При Ns1 начальная identity полного физического графа и индивидуальные
   параметры совпадают с записанным исходным N1-контролем. Проверка файла
   конфигурации без effective readback недостаточна.
2. Отдельный положительный контроль Ns2 создаёт дополнительные реальные
   компоненты синапса. Для совпадающих Branch-точек используется штатный общий
   `factor_control_job`, согласующий объявления одного физического банка.
   Это отдельное состояние; холодный Train по-прежнему начинается с Ns1.

При любом расхождении запуск Train запрещён. `preflight`-операция запроса
завершается после этих проверок и не создаёт обученной модели. Для настоящего
Train используется отдельная попытка и выполняются собственные свежие preflight.

## Владение процессами и данные

Запрос фиксирует код Python, SDK, точные входные файлы, runtime, ресурсы и
выходной каталог. Контроллер и нативные дочерние задания имеют отдельные
ограниченные группы. Общая резервация учитывает сумму максимальной памяти
контроллера и единственного одновременно работающего нативного процесса.
Сопровождение использует существующий точный supervisor `owned_native_job`:
PID, время создания, unit и конечный список дочерних каталогов сохраняются.
Резервация освобождается только после закрытия контроллера и всех его групп.
Старая живая попытка не перезапускается; данные и runtime не обновляются.

Во время расчёта проверяются небольшие неизменяемые входы. Git-дерево и весь
SDK не перечитываются каждый такт или каждую секунду. Полная проверка исходников
выполняется на границах операции, а фактически загруженный runtime фиксируется
стандартным backend.

После нативного Train результат остаётся `pending_full_primary_audit`.
Следующий отдельный процесс должен проверить всю сохранённую историю, затем
передать фактическую модель в калибровку и Test. Никакой шаблонный Test не
подставляется автоматически. Все полные модели, наблюдения и рисунки хранятся
во внешнем архиве; Git содержит этот код и небольшие квитанции.

Команды на Linux worker:

```text
python -m Scripts.StructTrain.TimeLearner count-training prepare /absolute/request.json
python -m Scripts.StructTrain.TimeLearner count-training launch /absolute/request.json
```

Запрос имеет kind `timelearner_linux_matched_count_training`, schema1.
Внешний количественный registry поддерживается в существующей версии2;
модуль не обновляет его схему и не заявляет поддержку любого scheduler.

## Границы сравнения и текущий статус

Для M40 имеется отдельный собранный SDK Root
`5b6cb11ee46ae196ecbf81003eec45654b4c3fad`, PulseLib
`1c8d0112061cb9025ef9205b0d8d735d62fcbe39`, Rdk
`561986e9f336ee5914e2d119de90b005e06f3639`. Три производственных исходника
Console Training/Transport/Probe побайтово совпадают с прежним Root
`bd9ea23aedd3520c2695fc6cb1d083921053f888`. Это не делает разные бинарники
или сервера одинаковыми: compiler/build/runtime сохраняются отдельно.

Контроль N1 выполнялся на Elder; новый N0 предполагается на M40. Различие
скорости машин меняет число кандидатов, успевших до wall-бюджета. Поэтому
такое сравнение не будет строгим однофакторным доказательством влияния
нормализации. Для него потребуется также согласованный N1-контроль на M40
с тем же SDK и протоколом. Пока это подготовка; успешное выполнение нового
Linux-пути, обучение и классификация ещё не объявляются.
