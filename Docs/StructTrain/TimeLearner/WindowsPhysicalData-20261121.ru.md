## 3 Условие следующего сравнения N0/N1

В исходном N1 search bounds для всех входов `maximum_synapses=1`, а у первых
трёх разрешён поиск Rs от1МОм до86МОм с дополнительной native проверкой
допустимости физики. Эти bounds корректны для данного N1; простое переключение
`model.normalization` в N0 оставило бы Ns неподвижным.

Для N0 требуется отдельная явная декларация: начальная физика и образы те же,
у обучаемых входов разрешён целочисленный диапазон Ns, Rs фиксирован на исходном
значении86МОм, опорный вход сохраняет Ns1/Rs86МОм/L1. Верхняя граница Ns сама
по себе не разрешает физически недопустимое состояние: проверка суммарных
проводимостей и интегратора остаётся обязательной. Это различие разрешённых
управлений двух алгоритмов, а не доказательство разных результатов по одному
флагу.

Новый `prepared_count_training.py` готовит сопоставимый холодный запуск Branch
с M=4. Изменяются только имя прогона, режим нормализации и соответствующие
управляющие bounds: у первых трёх входов Ns1…128, Rs86МОм; опорный вход
сохраняет Ns1/Rs86МОм/L1. Исходные образы, физика, паттерн, допуски и бюджеты
поиска сохраняются. Допустимость каждого кандидата по физике по-прежнему
проверяет native-код; разрешённый диапазон не является обещанием достижимости.

Перед Train выполняются два отдельных native preflight. Первый проверяет
реальную исходную модель Ns1; второй — положительный контроль применения
параметра: Ns2 только у первого входа, с проверкой фактического увеличения
числа узлов графа. Этот контроль не подменяет холодное начальное состояние
обучения. При отказе preflight Train не запускается. Исполнитель не приписывает
успехов прежним smoke-тестам и не выполняет действий при import.

Windows native ограничен16ГиБ и39600с, внутреннее время поиска —32400с.
Контроль диска работает в отдельном потоке; callback capture/ack только читает
готовое состояние и не обходит растущую историю. Полный аудит первичной истории
выполняется отдельно после закрытия native; до него терминальный статус явно
равен `pending_full_primary_audit`. Завершение процесса не означает сходимость.
Состояние конкретного задания фиксируется отдельной серверной квитанцией.
