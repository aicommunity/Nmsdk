# Резервирование предложений нормализации числом синапсов

23 ноября 2026 года. Подготовлена проверка изменения порядка предложений
V2, математическая цель и допуски сохраняются. Это не объявление принятого
исправления или нового положительного научного результата.

## Наблюдаемое ограничение

В фактических закрытых Classic и Branch траекториях после нескольких
улучшающихся амплитудных измерений ещё не проверен ближайший следующий
целый Ns. Функция `BoundedTrainingSession::PrioritizeN0Neighbors`
заранее расходует один конечный запас геометрии и на измеренный прогноз,
и на обычных соседей. Например, очередь может зарезервировать 2, 11, 3,
12, 10; затем результат измерения 12 уже не получает предложения 13.
Общий перебор продолжает работать и итог честно остаётся ограниченным
бюджетом. Это не доказательство недостижимости амплитуды.

## Предлагаемое изменение

Если по совместимым завершённым измерениям получен допустимый ещё
не предъявленный прогноз Ns, поставить только его. Обычных соседей
в этот момент не резервировать. После реального измерения снова
использовать существующую проверку совместимости, повторяемости,
монотонности, индивидуальных границ и конечного запаса.

```text
if valid unissued measured proposal exists and local allowance remains:
    enqueue that proposal
    consume one existing local reservation
    return
otherwise:
    retain existing bounded ordinary-neighbour fallback
```

Размеры запасов геометрии, кандидатов на вход, проб, изменений и проходов
не увеличиваются и не пополняются улучшением ошибки. Требуются новые
anchor/input measurements и свежая финальная проверка; прогноз ничего
не сертифицирует. N1, native lifecycle, storage и физическая модель
этим изменением не затрагиваются. Текущие серверные runtime неизменны.

## Проверка до допуска в научный опыт

Добавлены три проверки производственного `BoundedTrainingSession` на
контролируемых полных наблюдениях: Classic, Branch и испорченный финальный
отклик. В ограничении восемь кандидатов ожидается последовательность
1→2→11→12→13, где для решения нужны несколько реальных уточнений,
а первое предложение не выполняет амплитудный допуск. Испорченный
финальный отклик обязан оставить результат не-Exact.

Повторно используется существующий compiled A/B путь с отдельным именем
N0-проверки: полный production C++ target, одинаковый набор новых и прежних
тестов, точные root/Pulse commits, compiler/dependency hashes, фактические
loaded files и JUnit. До изменения должны отказать ровно три новых теста;
после — пройти весь объявленный набор без skips. Тела функций не копируются.

Это проверка алгоритмического ядра. Затем отдельно нужны native SDK
regression и физическое A/B при сопоставимых условиях, с полными первичными
данными и временными графиками. Контролируемый отклик не доказывает
сходимость физической модели. Сначала закрываются живые опыты и их
приоритетная упаковка; новые исходники и сборки создаются отдельно.
